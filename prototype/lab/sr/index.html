Data to send, and no permission.
All the phone may send is one bit.

A phone cannot transmit data until the base station grants it room. So when data shows up and there is no grant, it uses a tiny reserved slot to raise its hand. That is a scheduling request. Then it waits, asks again if nothing comes, and eventually gives up on asking politely. Give the phone some data and watch.

What happened, in order

    The whole story, from zero

    1. Uplink needs permission

      A phone sends data only inside a grant from the base station (gNB). When new data appears and it holds no grant, it has nothing to send the data in, and nothing to send a buffer report in either.

    2. A reserved slot to raise a hand

      The gNB sets aside a small recurring slot on the uplink control channel for each phone. The slot returns every few milliseconds whether it is used or not.

    3. The request is one bit

      In its next slot the phone sends a scheduling request. It says only that something is waiting. How much comes later, in the buffer status report.

    4. Then it must hold still

      Sending starts a prohibit timer. Until that timer ends the phone may not ask again, which gives the gNB time to answer and keeps the control channel quiet.

    5. No grant yet: ask again and count

      If the timer ends and no grant has come, the phone asks again in the next slot. A counter tracks how many requests it has sent for this need.

    6. Too many unanswered: change channel

      When the counter reaches its limit, the phone concludes that its requests are not getting through. It gives up its reserved slots and starts random access, the same door a stranger would use.

    Once a grant arrives, the phone sends its data and a buffer report in it, and the pending request is cancelled. While a request is pending, the phone also stays awake to hear the answer, whatever its sleep schedule says.

    What each number is for

    The gNB sets these per phone by RRC. A phone can have several request configurations, so urgent data can ask through a faster one.

    How soon can the phone ask?
    SR periodicity and offset
    from a couple of symbols to 640 slots
    A short period means a short wait for the first request. Every slot is reserved for this one phone and sits empty most of the time, so a busy cell cannot give everyone a short one.
    How long before it may ask again?
    sr-ProhibitTimer
    1 to 128 ms
    Shorter than the gNB's reaction time, the phone repeats itself before the answer can arrive, which wastes requests and can earn it a second grant it does not need. Much longer, and a missed request takes a long time to repair.
    How many tries before giving up on asking?
    sr-TransMax
    4, 8, 16, 32 or 64
    Low falls back to random access quickly when the uplink is broken, and too readily on a merely bad day. High keeps a phone repeating requests nobody can hear.

    What this lab simplifies. One phone, one request configuration, one slot per millisecond. Every grant is large enough to empty the buffer, so one grant ends the story; sizing grants is the job of the buffer status report. Whether the gNB hears a request is a coin flip at the rate you set. The random access fallback takes a fixed 60 ms and always works, and afterwards the reserved slots are assumed to be configured again. Not modelled: several request configurations and their mapping to logical channels, requests triggered by beam failure or other causes, the delay timer for low-priority data, overlap with other uplink transmissions, and DRX.
